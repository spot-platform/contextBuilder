# 4. Implementation

## 4.1 시스템 개요

본 시스템은 카카오 Local API에서 수집한 원본 장소 데이터를 정제·피처화하는 **배치 ETL 단(local-context-builder)**, 페르소나 기반 에이전트가 결정론적으로 행동하는 **에이전트 시뮬레이션 단(spot-simulator)**, 그리고 시뮬레이션 로그를 LLM으로 5종 합성 콘텐츠로 변환하고 6-계층 검증으로 승인하는 **합성 콘텐츠 단(synthetic-content-pipeline)**의 세 파이프라인으로 구성된다. 세 파이프라인은 각각 독립 Python 패키지로 분리되어 있으며, 데이터는 PostgreSQL과 JSONL 파일을 통해 단방향으로만 전달된다.

## 4.4 Pipeline 1 — `local-context-builder`

**역할.** 카카오 Local API → 정규화 → 지역 피처 → 페르소나 가중치 → 데이터셋 버전 발행.

### 4.4.1 모듈 구조 (`app/`)

```
app/
├── api/admin.py                        # FastAPI 라우터 (14개 엔드포인트, X-Admin-Key 헤더 인증)
├── celery_app.py                       # Celery 워커 진입점
├── collectors/                         # 외부 데이터 수집
│   ├── kakao_local_client.py           # httpx 동기 클라이언트, 200 ms pacing, 3-page cap
│   ├── grid_strategy.py                # 행정동 ↔ (x, y, radius) grid 분할
│   ├── category_collector.py           # 카카오 category group 수집
│   ├── keyword_collector.py            # 키워드 검색 수집
│   └── region_master_loader.py         # 행정동 시드
├── processors/                         # 데이터 변환
│   ├── normalize_places.py             # 중복 제거 (rapidfuzz)
│   ├── category_mapper.py              # 룰 기반 카테고리 매핑
│   ├── build_region_features.py        # 5 density + 3 access + 4 suitability
│   ├── build_persona_region_weights.py
│   └── build_spot_weights.py
├── services/                           # 점수/배포 보조
│   ├── scoring_service.py              # percentile_rank, sigmoid_normalize, weighted_avg
│   ├── feature_service.py
│   ├── attractiveness_service.py
│   └── publisher_service.py
├── jobs/                               # Celery 태스크 (bootstrap_regions, full_rebuild,
│                                       #  incremental_refresh, build_all_features,
│                                       #  merge_real_data, publish_dataset, ...)
├── models/                             # 9개 SQLAlchemy 모델 (DDL: migrations/0001)
└── monitoring/                         # health_checks, metrics, alerts
```

### 4.4.2 데이터 모델 (PostgreSQL 9 테이블)

`region_master`, `place_raw_kakao`, `place_normalized`, `category_mapping_rule`, `region_feature`, `real_activity_agg`, `persona_region_weight`, `spot_seed_dataset`, `dataset_version` — 단일 Alembic 리비전(`0001_initial_schema.py`)으로 정의.

### 4.4.3 핵심 알고리즘

- **수집 페이싱.** `KakaoLocalClient`는 매 호출 후 200 ms `time.sleep`, 429/5xx에 대해 `2^attempt + jitter` 지수 백오프, `Retry-After` 헤더 파싱. 페이지 상한 `MAX_PAGES = 3`, `PAGE_SIZE = 15`로 카카오 일일 쿼터(`§5-2`)를 보장한다.
- **장소 정규화.** `(name, road_address)` 튜플에 대해 `rapidfuzz.fuzz.token_set_ratio ≥ 90`을 동일 후보로 클러스터링하여 중복 제거.
- **지역 피처.** _전체 도시 단위 백분위순위(percentile rank)_ 후 sigmoid 정규화로 0–1 스코어. 단일 지역 단위 호출은 ranking이 정의되지 않으므로 도시 전체 배열로 `numpy.argsort` 한 번 호출.
- **블렌딩.** `blended = α · kakao_raw + β · real_data_score`. MVP는 `α = 1, β = 0` (실데이터 미연동 stub).
- **버전 발행.** `publish_dataset`은 `(dataset_version)` 키로 append-only upsert를 수행하며, 발행 후 `dataset_version` 테이블의 `published_at`만 갱신한다. 롤백은 새 버전을 발행하지 않고 이전 버전 row의 `is_active = TRUE`로 복귀.

### 4.4.4 운영 인터페이스

`/admin/{bootstrap, full-rebuild, incremental-refresh, build-features, publish}` POST 엔드포인트가 Celery에 작업을 enqueue 하고, 동기 GET (`status`, `dataset/latest`, `dataset/versions`, `region/{id}`, `metrics`)이 진행 상황과 데이터를 반환한다. `/admin/health`만 인증 면제(liveness probe).

## 4.5 Pipeline 2 — `spot-simulator`

**역할.** 페르소나·지역 가중치를 입력으로 받아 N명의 에이전트를 T tick 동안 시뮬레이션하고, 모든 의사결정·라이프사이클 전이·정산을 `event_log.jsonl`로 기록.

### 4.5.1 모듈 구조

```
spot-simulator/
├── main.py                             # CLI 진입 (phase, run_id, seed)
├── models/                             # 5 dataclass: AgentState, Spot, EventLog,
│                                       #  SettlementResult, SkillProfile/Assets/Relationship
├── data/
│   ├── loader.py                       # YAML/JSON 로더 (config, persona, region)
│   ├── adapters.py                     # region_create_affinity, category_match, budget_penalty
│   └── agent_factory.py                # init_agent_from_persona
├── engine/                             # 16개 모듈 — 결정론적 tick 루프
│   ├── runner.py                       # 메인 루프 (legacy / peer 두 모드)
│   ├── decay.py                        # fatigue ↓ / social_need ↑
│   ├── decision.py                     # p_create, p_join 산정
│   ├── lifecycle.py                    # OPEN → MATCHED → IN_PROGRESS → ...
│   ├── executors.py                    # action 실행 + 이벤트 emit
│   ├── settlement.py                   # Phase 3 정산 + 신뢰 갱신
│   ├── negotiation.py                  # peer pivot: counter-offer
│   ├── peer_decision.py                # p_teach / p_learn / p_post_request

│   ├── time_availability.py            # schedule_weights 적용
│   ├── wallet_tracker.py               # 잔액 추적

└── analysis/                           # validate.py, visualize.py
```

### 4.5.2 데이터 모델 (Python `dataclass`)

`AgentState`는 _append-only_ 정책에 따라 Phase 1→3을 거치며 필드만 추가된다(아이덴티티/성향/동적 상태/스케줄/추적/Phase 2 신뢰·확정 스팟/Phase 3 리뷰·만족도 이력). 모든 동적 변수는 `dataclass(frozen=False)`로 in-place 갱신, 모델 재생성을 피해 GC 부담을 낮춘다.

### 4.5.3 결정 함수 (식 1)

Phase 2 기준,

$$
p_{\text{create}} = 0.35\, h + 0.20\, a_r + 0.25\, s - 0.15\, f - 0.10\, \pi_{\text{recent}} \tag{1a}
$$

$$
\begin{aligned}
p_{\text{join}} = \,& 0.25\, j + 0.20\, c_m + 0.15\, s + 0.15\, m_{\text{social}} \\
&+ 0.10\, a_r - 0.10\, f - 0.05\, b_p
\end{aligned}
\tag{1b}
$$

여기서 $h, j$는 host/join 성향, $a_r$은 지역 친화도, $c_m$은 카테고리 적합도, $s$는 사회적 욕구, $f$는 피로도, $m_{\text{social}}$은 친분 보정, $b_p$는 예산 페널티이다. 두 확률은 $[0,1]$로 클램프되며, 모든 난수는 외부 주입된 `random.Random` 한 인스턴스에서만 추출되어 시드 동일 시 바이트 단위로 동일한 `event_log`가 생성된다.

### 4.5.4 라이프사이클 FSM

`OPEN → MATCHED → CONFIRMED → IN_PROGRESS → CHECKED_IN → CLOSED` 정상 경로에 `CANCELED` / `NO_SHOW` 분기. Phase 2부터는 매 tick 의사결정 직전에 `process_lifecycle`이, 직후에 `check-in` / `cancel` 패스가 추가되며, Phase 3에서는 `process_settlement`가 만족도·신뢰·분쟁 해소를 적용한다.

### 4.5.5 스케일

| Phase          | 에이전트 | tick | 결정 횟수 | 측정된 실행시간 |
| -------------- | -------: | ---: | --------: | --------------: |
| 1 (MVP)        |       50 |   48 |     2,400 |           < 5 s |
| 2 (lifecycle)  |      500 |  168 |    84,000 |          < 30 s |
| 3 (settlement) |    5,000 |  336 |    1.68 M |         < 3 min |

**역할.** 시뮬레이션 로그를 입력으로 받아 5종 합성 콘텐츠를 생성하고, 6-계층 검증을 통과한 결과만 publish.

### 4.6.2 LLM 호출 브리지 (`codex_client.py`)

OpenAI / Anthropic API 키를 사용하지 **않는다.** 사용자 Codex 구독 CLI를 다음과 같이 호출한다.

```python
subprocess.run(
    ["codex", "exec", "-m", model, "--json"],   # ALLOW_CODEX_SUBPROCESS
    input=prompt,
    capture_output=True,
    timeout=90,
)
```

- 동시성: `BoundedSemaphore`(`SCP_CODEX_CONCURRENCY`, 기본 2)
- 캐시: `(template_id, variables-hash)`로 결과 재사용
- stub 모드: `SCP_LLM_MODE=stub`이면 `tests/fixtures/codex_stub/{tpl}/v{n}/{key[:8]}.json`로 폴백
- `subprocess` 호출은 `codex_client.py`로만 한정되고, `scripts/lint_no_api.py`가 다른 모듈의 `subprocess`/`requests` 사용을 정적 검사하여 차단

### 4.6.3 6-계층 검증

| Layer              | 모듈                 | 검사 내용                                                 | 차단/감점 |
| ------------------ | -------------------- | --------------------------------------------------------- | --------- |
| L1 Schema          | `schema.py`          | `jsonschema`로 필수 필드/타입                             | 차단      |
| L2 Rule            | `*_rules.py` 7종     | 길이/포맷/페르소나 톤/단어 금칙                           | 차단      |
| L3 Cross-reference | `cross_reference.py` | 생성 텍스트의 사실이 `event_log` 및 `content_spec`과 일치 | 차단      |
| L4 Critic          | `critic.py`          | LLM(via codex bridge) 샘플링 비평 — 4점수 산정            | 가중치    |
| L5 Diversity       | `diversity.py`       | 3-gram Jaccard / TF-IDF cosine / 템플릿 regex의 max       | 가중치    |
| L6 Scoring         | `scoring.py`         | 식 (2)로 통합 후 임계치 비교                              | 분류      |

### 4.6.4 품질 점수 (식 2)

$$
\begin{aligned}
Q = \,& 0.25\, \text{naturalness} + 0.20\, \text{consistency} + 0.15\, \text{persona\_fit} \\
&+ 0.10\, \text{region\_fit} + 0.05\, \text{rule\_fit} + 0.10\, \text{diversity} \\
&+ 0.15\, \text{peer\_tone\_fit}
\end{aligned}
\tag{2}
$$

분류 임계치: $Q \ge 0.80$ → `approved`, $0.65 \le Q < 0.80$ → `conditional`(재시도), $Q < 0.65$ → `rejected`. 가중치는 `config/weights/scoring_weights.json`과 동기화되며 합 1.00이 단위 테스트로 강제된다.

### 4.6.5 재시도 루프

L1–L3에서 차단 시 `retry.py`가 reject 사유를 jinja2 컨텍스트로 주입하여 동일 generator를 재호출한다. 최대 N회(generator당 기본 2 candidate × 최대 2회) 시도 후에도 통과하지 못하면 해당 spot의 콘텐츠는 publish에서 제외된다.

## 4.7 데이터 흐름과 단방향 결합

세 파이프라인은 코드를 직접 import 하지 않고, 다음 두 경계면으로만 연결된다.

1. **LCB → Sim**: `dataset_version`이 published 상태인 `region_feature`, `persona_region_weight`, `spot_seed_dataset`을 PostgreSQL에서 읽어 `data/loader.py`의 `load_region_features` / `load_persona_region_affinity`가 in-memory dict로 적재한다.
2. **Sim → SCP**: `event_log.jsonl`이 `pipeline.spec.builder`의 입력이 되어 `content_spec`(스팟 단위 사실 묶음)으로 정규화된 뒤 generator에 주입된다.

이 단방향 결합 덕분에 각 파이프라인은 독립적으로 재실행/롤백/A-B 테스트가 가능하며, 본 시스템에서는 LCB의 `dataset_version`과 SCP의 `content_version_policy`가 매핑 표로 묶여 동일 `dataset_version`에 대한 합성 콘텐츠 재현이 보장된다.

## 4.8 재현(reproducibility) 설정

- **결정론**: Sim의 모든 난수 — `decision`, `lifecycle`, `settlement`, `peer_decision` — 는 단일 `random.Random(seed)` 인스턴스로부터 추출되며 동일 seed + 동일 입력 데이터셋이면 `event_log.jsonl`이 바이트 동일.
- **버전 고정**: LCB는 `dataset_version` 행에 카카오 수집 시점·매핑 룰 버전을 기록, SCP는 `template_id v{n}` + `scoring_weights.json` SHA를 함께 publish 메타데이터에 저장.
- **컨테이너**: LCB는 `docker-compose`(app + PostgreSQL 15 + Redis 7)로 단일 명령 기동. Sim/SCP는 `pip install -e .` 후 CLI로 실행.
- **테스트 격리**: SCP는 `SCP_LLM_MODE=stub`로 fixture 응답을 사용해 외부 호출 없이 39개 테스트 전체를 CI에서 실행 가능.
